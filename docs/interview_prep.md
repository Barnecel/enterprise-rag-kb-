# 面试复盘 & 项目速答手册（企业知识库 RAG 系统）

> 适用场景：技术面试被拷打时的自救手册。所有数字来自本地压测/监控真实采集，非编造。

## 一、项目一句话定位
混合检索（BM25+向量）+ 多模型热插拔 + 评测驱动的企业级 RAG 问答平台。
Flask + Vue3 + LangChain + ChromaDB + Cross-Encoder + 本地化大模型(Qwen3)。

## 一-B、系统说明（给面试官/评审的完整画像）

### 业务背景
面向企业内部知识库（公安执法考试资料、制度文档、技术手册等多领域语料，单文档切分达 1323 章节块）
的智能问答系统。目标是在"检索准 + 作答全 + 权限严"三重约束下，提供可审计、可热插拔、可评测的 RAG 服务。

### 架构分层（请求生命周期）
```
用户提问
  │ ① 语义缓存层 ── 命中 → 直接返回（跳过检索+生成，热点问题 TTFT 近 0）
  │ 未命中
  │ ② 理解层 ── 查询改写（指代消解 + 多变体扩展 + 领域同义规则，带缓存保证确定性）
  │ ③ 检索层 ── 稠密路(Embedding→Chroma) ┐
  │           稀疏路(jieba→BM25) ─────────┴→ RRF 融合 → Cross-Encoder 重排
  │                                      → 置信度兜底 → 动态 TopK → 父窗口扩展
  │ ④ 生成层 ── 提示词模板 → LLM 流式生成(SSE)
  │ ⑤ 落地层 ── 问答历史 → 语义缓存回写 → 点赞/点踩反馈 → badcase 转金标
```

### 关键工程决策
- **混合检索**：BM25（词法精确）+ 向量（语义泛化）双路召回，RRF 融合，单路故障自动兜底
- **父子索引**：小子块精准匹配、父窗口完整作答，兼顾精度与上下文完整性
- **多租户 + 密级 + ACL**：部门隔离、密级门槛、显式授权三级可见性，权限元数据双库同步
- **模型热插拔**：LLM/嵌入经注册表运行时切换（OpenAI 兼容协议），切换自动清理语义缓存
- **评测驱动**：57 题双粒度金标集（文档级 Recall + 章节级关键词命中）+ LLM-as-Judge A/B 盲评

## 二、真实性能指标（压测 + Prometheus 实测）

> 采集方式：Locust 20 并发压测产出端到端延迟；`/metrics` 端点暴露检索各阶段 Histogram，
> 用 `histogram_quantile` 算出 P50/P95。全部为本地环境真实数据，非估算。

### 检索管线（RAG 内核，毫秒~秒级）
| 阶段 | P50 | P95 | 备注 |
|------|-----|-----|------|
| BM25 词法召回 | 10ms | 50ms | jieba 分词 + 倒排，受词表规模影响极小 |
| RRF 倒数排名融合 | 10ms | 10ms | 双路合并，纯内存排序 |
| Vector 稠密召回 | ~2s | >10s | 含一次 embedding API 调用，本地 oMLX 端点波动导致长尾 |
| Cross-Encoder 重排 | 1s | 2s | BAAI/bge-reranker-base 对 Top-15 精排为 Top-8 |
| **检索全链路** | **~3s** | — | 与生成相比可忽略 |

### 端到端（Locust 20 并发压测）
- `/api/qa/ask`：P50=53s，P95=154s，P99=169s，0 失败
- `/api/auth/login`：P50=0.49s
- `/api/health`：P50=4ms
- 长杆 = **LLM 生成**（本地 9B / 局域网 27B 算力受限），非检索管线

### 长杆定位（关键结论）
把端到端延迟拆成"检索全链路 ~3s"与"LLM 生成 ≥30s"两部分后，结论非常清晰：
**RAG 管线本身极快，瓶颈 100% 在生成侧**。具体证据链：
1. 检索各阶段 Prometheus 埋点显示 BM25/RRF 在 10ms 级，Vector/Rerank 在秒级，全链路 ~3s；
2. 同一请求在 Locust 中 P99=169s，减去 ~3s 检索后，生成耗时占 98% 以上；
3. 切换不同模型（9B 本地 vs 27B 局域网）延迟数量级不变，印证是"算力/网络"而非"代码"问题。

### 优化 roadmap（面试加分项）
| 方向 | 预期收益 | 实现要点 |
|------|----------|----------|
| 语义缓存（L1/L2/L3） | 热点问题 TTFT 近 0，整体 QPS 提升 | 已落地三级缓存 + 热点自动写回 |
| 模型量化/蒸馏 | 生成延迟降 2~5x | 已用 4bit 量化模型，可进一步蒸馏小模型 |
| 流式首 token 优先 | 用户感知延迟从"等全答"变"秒出首字" | SSE 流式已支持 |
| 检索侧异步化 | 检索与部分预处理与生成重叠 | 可后续演进 |

### 结论话术
> "检索与重排全链路在秒级内完成，端到端 TTFT 的长杆是本地大模型生成（占 98%+）。
> 我通过 Prometheus 把检索各阶段拆开埋点定位到这一点，而不是靠猜。
> 优化方向：语义缓存命中（热点问题跳过检索+生成）、模型量化/蒸馏、流式首 token 优先返回。"

## 三、面试高频问题 + 标准答

### Q1：为什么用混合检索而不是纯向量？
A：BM25 保证词法精确召回（专有名词、编号、法条），向量捕语义泛化；
RRF 融合避免单路权重主导；任一路故障另一路兜底，Recall@5 实测 1.0。

### Q2：父子索引解决什么？
A：子块小（精准匹配）但上下文碎；父窗口（完整段落）作生成上下文。
1323 章节块语料上，子块命中+父窗口作答，Recall@5=1.0 且答案可读。

### Q3：如何保证多租户/密级隔离？
A：文档带 tenant_id + doc_level + 显式 ACL；检索前拼 WHERE 过滤，
Chroma 元数据过滤 + MySQL 授权双库同步，前端按权限显隐。

### Q4：模型热插拔怎么实现？
A：注册表模式，LLM/嵌入配置存 DB；切换经 `hot_swap_llm`/`hot_swap_embedding`，
LLM 切换即清语义缓存，嵌入切换先探测维度不兼容则要求重建向量库。
**踩过的坑（已修）**：① 启动未加载 DB 激活模型，重启丢切换；② 嵌入误用 LLM 的 api_key。

### Q5：评测体系怎么建？
A：57 题双粒度金标（文档级 Recall + 章节关键词命中），以评测为安全网做零行为变更重构；
LLM-as-Judge A/B 盲评（位置随机化防偏），9B vs 27B 量化 99.3 vs 95.3（200 分制）。

### Q6：可观测性怎么做的？
A：Prometheus 埋点（HTTP 延迟、检索各阶段、缓存命中、生成延迟）+ /metrics 暴露 +
Grafana 面板；Locust 压测出 P50/P95/P99。缓存命中率/检索分解均可直接看图。

### Q7：最大技术挑战？
A：OCR 断行导致"检索/评测/验证同时失明"（CJK 不可见换行符），
正则连通 + 单测固化，Recall 从 0.67 恢复到 1.0。

## 四、被追问时的安全边界
- 缓存命中率具体数字：看 Grafana `cache_hit_total/(cache_hit+cache_miss)`，本机未跑满不做预估
- 并发上限：Chroma 单机 ~150 QPS 估算值，未做分布式压测验证
- 绝不报编造数字；答"我项目里埋了点，实际跑一下就有，结论是长杆在生成"
