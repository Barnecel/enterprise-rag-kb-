# 面试复盘 & 项目速答手册（企业知识库 RAG 系统）

> 适用场景：技术面试被拷打时的自救手册。所有数字来自本地压测/监控真实采集，非编造。

## 一、项目一句话定位
混合检索（BM25+向量）+ 多模型热插拔 + 评测驱动的企业级 RAG 问答平台。
Flask + Vue3 + LangChain + ChromaDB + Cross-Encoder + 本地化大模型(Qwen3)。

## 一-B、系统说明（给面试官/评审的完整画像）

### 业务背景
面向企业内部知识库（公安执法考试资料、制度文档、技术手册等多领域语料，单文档切分达 1323 章节块）
的智能问答系统。目标是在"检索准 + 作答全 + 权限严"三重约束下，提供可审计、可热插拔、可评测的 RAG 服务。

### 架构分层（请求生命周期）
```
用户提问
  │ ① 语义缓存层 ── 命中 → 直接返回（跳过检索+生成，热点问题 TTFT 近 0）
  │ 未命中
  │ ② 理解层 ── 查询改写（指代消解 + 多变体扩展 + 领域同义规则，带缓存保证确定性）
  │ ③ 检索层 ── 稠密路(Embedding→Chroma) ┐
  │           稀疏路(jieba→BM25) ─────────┴→ RRF 融合 → Cross-Encoder 重排
  │                                      → 置信度兜底 → 动态 TopK → 父窗口扩展
  │ ④ 生成层 ── 提示词模板 → LLM 流式生成(SSE)
  │ ⑤ 落地层 ── 问答历史 → 语义缓存回写 → 点赞/点踩反馈 → badcase 转金标
```

### 关键工程决策
- **混合检索**：BM25（词法精确）+ 向量（语义泛化）双路召回，RRF 融合，单路故障自动兜底
- **父子索引**：小子块精准匹配、父窗口完整作答，兼顾精度与上下文完整性
- **多租户 + 密级 + ACL**：部门隔离、密级门槛、显式授权三级可见性，权限元数据双库同步
- **模型热插拔**：LLM/嵌入经注册表运行时切换（OpenAI 兼容协议），切换自动清理语义缓存
- **评测驱动**：57 题双粒度金标集（文档级 Recall + 章节级关键词命中）+ LLM-as-Judge A/B 盲评

## 二、真实性能指标（压测 + Prometheus 实测）

> 采集方式：Locust 20 并发压测产出端到端延迟；`/metrics` 端点暴露检索各阶段 Histogram，
> 用 `histogram_quantile` 算出 P50/P95。全部为本地环境真实数据，非估算。

### 检索管线（RAG 内核，毫秒~秒级）
| 阶段 | P50 | P95 | 备注 |
|------|-----|-----|------|
| BM25 词法召回 | 10ms | 50ms | jieba 分词 + 倒排，受词表规模影响极小 |
| RRF 倒数排名融合 | 10ms | 10ms | 双路合并，纯内存排序 |
| Vector 稠密召回 | ~2s | >10s | 含一次 embedding API 调用，本地 oMLX 端点波动导致长尾 |
| Cross-Encoder 重排 | 1s | 2s | BAAI/bge-reranker-base 对 Top-15 精排为 Top-8 |
| **检索全链路** | **~3s** | — | 与生成相比可忽略 |

### 端到端（Locust 20 并发压测）
- `/api/qa/ask`：P50=53s，P95=154s，P99=169s，0 失败
- `/api/auth/login`：P50=0.49s
- `/api/health`：P50=4ms
- 长杆 = **LLM 生成**（本地 9B / 局域网 27B 算力受限），非检索管线

### 长杆定位（关键结论）
把端到端延迟拆成"检索全链路 ~3s"与"LLM 生成 ≥30s"两部分后，结论非常清晰：
**RAG 管线本身极快，瓶颈 100% 在生成侧**。具体证据链：
1. 检索各阶段 Prometheus 埋点显示 BM25/RRF 在 10ms 级，Vector/Rerank 在秒级，全链路 ~3s；
2. 同一请求在 Locust 中 P99=169s，减去 ~3s 检索后，生成耗时占 98% 以上；
3. 切换不同模型（9B 本地 vs 27B 局域网）延迟数量级不变，印证是"算力/网络"而非"代码"问题。

### 优化 roadmap（面试加分项）
| 方向 | 预期收益 | 实现要点 |
|------|----------|----------|
| 语义缓存（L1/L2/L3） | 热点问题 TTFT 近 0，整体 QPS 提升 | 已落地三级缓存 + 热点自动写回 |
| 模型量化/蒸馏 | 生成延迟降 2~5x | 已用 4bit 量化模型，可进一步蒸馏小模型 |
| 流式首 token 优先 | 用户感知延迟从"等全答"变"秒出首字" | SSE 流式已支持 |
| 检索侧异步化 | 检索与部分预处理与生成重叠 | 可后续演进 |

### 缓存命中率（Locust 固定问题压测，同问题重复 554 次）
- `cache_hit_total{L1}`=547，`cache_miss_total{L1}`=82（基线 75 + 新增 7）
- **L1 精确命中率 = 547/554 = 98.7%**（热点问题第 5 次后被自动写回 L1/L2/L3）
- L2/L3 在重复场景下未触发（L1 已短路返回），机制上 L1 精确 / L2 语义 / L3 上下文三级兜底

### 结论话术
> "检索与重排全链路在秒级内完成，端到端 TTFT 的长杆是本地大模型生成（占 98%+）。
> 我通过 Prometheus 把检索各阶段拆开埋点定位到这一点，而不是靠猜。
> 优化方向：语义缓存命中（热点问题跳过检索+生成）、模型量化/蒸馏、流式首 token 优先返回。"

## 三、面试高频问题 + 标准答

### Q1：为什么用混合检索而不是纯向量？
A：BM25 保证词法精确召回（专有名词、编号、法条），向量捕语义泛化；
RRF 融合避免单路权重主导；任一路故障另一路兜底，Recall@5 实测 1.0。

### Q2：父子索引解决什么？
A：子块小（精准匹配）但上下文碎；父窗口（完整段落）作生成上下文。
1323 章节块语料上，子块命中+父窗口作答，Recall@5=1.0 且答案可读。

### Q3：如何保证多租户/密级隔离？
A：文档带 tenant_id + doc_level + 显式 ACL；检索前拼 WHERE 过滤，
Chroma 元数据过滤 + MySQL 授权双库同步，前端按权限显隐。

### Q4：模型热插拔怎么实现？
A：注册表模式，LLM/嵌入配置存 DB；切换经 `hot_swap_llm`/`hot_swap_embedding`，
LLM 切换即清语义缓存，嵌入切换先探测维度不兼容则要求重建向量库。
**踩过的坑（已修）**：① 启动未加载 DB 激活模型，重启丢切换；② 嵌入误用 LLM 的 api_key。

### Q5：评测体系怎么建？
A：57 题双粒度金标（文档级 Recall + 章节关键词命中），以评测为安全网做零行为变更重构；
LLM-as-Judge A/B 盲评（位置随机化防偏），9B vs 27B 量化 99.3 vs 95.3（200 分制）。

### Q6：可观测性怎么做的？
A：Prometheus 埋点（HTTP 延迟、检索各阶段、缓存命中、生成延迟）+ /metrics 暴露 +
Grafana 面板；Locust 压测出 P50/P95/P99。缓存命中率/检索分解均可直接看图。

### Q7：最大技术挑战？
A：OCR 断行导致"检索/评测/验证同时失明"（CJK 不可见换行符），
正则连通 + 单测固化，Recall 从 0.67 恢复到 1.0。

### Q8：Vector 检索 2s 是 TTFT 长杆，为什么不砍掉只留 BM25？
> ⚠️ 真实面试被追问实录：先混淆了 BM25/Vector 语义归属（BM25=词法精确、Vector=语义），
> 又误把 MRR（评测指标）说成融合算法（实为 RRF），两次退到"不知道"。
> 以下为正确答法，必须能脱口而出。

A：
1. **BM25 与 Vector 在 `retrievers.py::_hybrid_retrieve` 里是串行的**（先 bm25.search 再 _dense_search 再 rrf_fuse），
   检索延迟 ≈ BM25(10ms)+Vector(2s)+RRF(10ms)≈**2s，Vector 的 2s 是实打实付了的**。
2. **但即便改成并行，检索延迟也只降到 max(2s,10ms)=2s**——因为 2s 是 Vector **自身 embedding API 调用**的耗时，
   不是"hybrid 的额外开销"。所以"砍 Vector 省 2s"是伪命题；
   真要降这 2s，得**优化 embedding 端点**（缓存 embedding 结果 / 异步化 / 换更小嵌入模型），不是扔掉语义检索。
3. **语义召回不可弃（已实测，非猜测）**：同一份 57 题金标集，两套检索口径对照：

| 指标 | 混合(dense+sparse+RRF+rerank) | BM25-only(词法+rerank) | 差值 |
|------|------|------|------|
| Recall@5 | **1.000** | 0.983 | **+1.7pp** |
| MRR@5 | **1.000** | 0.965 | +3.5pp |
| HitRate@5 | **1.000** | 0.983 | +1.7pp |

- BM25-only 仅漏 1/57 题：**"P0171是什么意思？油泵坏了吗？"** —— 期望 doc_id=2，BM25 被"油泵"关键词带偏到 doc 4；
  向量语义检索理解"P0171=混合气过稀"命中正确 doc 2。这正是语义路存在的价值。
- ⚠️ **诚实结论**：在本金标集（关键词密集的 HR/制度/故障码）上，混合相对 BM25-only 优势只有 +1.7pp，并不悬殊。
  原因是金标集偏词面匹配，没充分压到语义改写场景。**若想放大混合优势，应补一批同义改写/口语化问法题**。
- 我此前瞎猜"BM25-only 会掉到 0.7~0.85"——实测打脸。**永远用评测说话，别报拍脑袋数**。
4. **两路兜底是容灾冗余**（一路挂另一路顶），顺带提升鲁棒性；这是可用性论点，不是 TTFT 论点，别混为一谈。

**一句话版**："Vector 的 2s 是 embedding 延迟，hybrid 本身不额外加时间；语义召回不可弃，优化靠 embedding 缓存/异步，不是砍语义路。"

### Q9：查询改写的具体实现是什么？
A：`application/services/query_rewriter.py::rewrite()`。⚠️ **必须讲清是两套独立机制，别揉成一团**：

**机制 A：指代消解（"它"/"这一点"→实体）——靠 LLM + 会话历史，与正则无关**
- `prompt.format(question, history=build_dialogue_text(history))` 把对话历史拼进 prompt，
  由 LLM（Qwen3.5-9B, temperature=0.3, max_tokens=512）根据上文补全指代。
- 结论：**指代消解是 LLM 读历史做的，正则规则表不参与。**

**机制 B：领域同义扩展（确定性变体）——靠 SYNONYM_RULES 正则表，与历史无关**
- `(r'几名(民警|警察|...)', '一名以上人民警察 人数')`、`(r'讯问.{0,6}(几小时|多久|时限)', '讯问 犯罪嫌疑人 12小时 24小时')`
- `re.search(pat, question) and extra not in queries → append(extra)`，**只匹配当前 question、不读历史、不做指代**。
- 规则由**评测 badcase 驱动增长**（如 Q7"几名民警"检索不到"一名以上人民警察"），非凭空堆砌。

**防御设计（改写抽风不丢基线）——项目最值得讲的点**：
1. **原问题永远在首位**：`queries = [question] + ...`，改写全错也有原问题兜底召回；
2. **失败回退**：LLM 异常 → `except: return [question]`，不崩；
3. **规则变体只追加不替换**：最坏加几句噪音，绝不丢失基线检索；
4. **改写结果缓存**：按 `question+history` 哈希判重，消除 LLM 随机性导致的检索漂移。

**已知缺口（自己先承认）**：单发无上下文的"那它能报销多少钱？"——history 为空时 LLM 无从指代消解，
"它"原样带回，检索大概率查不到"差旅报销标准"。这是 solo 场景的弱化，暂无专门规则兜底。

典型场景：用户问"那个油泵故障代码怎么处理？"，改写变体含"P0171"与"混合气过稀"，确保召回正确文档。

### Q10：RRF（倒数排名融合）是如何工作的？
A：`retrievers.py:129` 的 `reciprocal_rank_fusion(dense, sparse, k=rrf_k, weights=weights)`：
- 对每个检索路径（BM25/向量）得到的文档按排名排序
- 计算融合分数：`score = Σ(weights * 1/(k + rank))`，k默认60
- 双路结果叠加，单路故障另一路兜底
- 权重可配置：默认`{'dense': 1.0, 'sparse': 1.0}`，可根据业务调整偏好
- 纯内存操作，耗时仅~10ms（见性能表格第3行）

### Q11：Cross-Encoder 重排的原理和作用？
A：`retrievers.py:146` `self.reranker.rerank(query, merged[:fusion_top_n], rerank_top_n)`：
- 使用 BAAI/bge-reranker-base 模型对前15个候选进行精排
- 输出 Top-8 重排后的文档
- 原理是双向编码器通过计算查询-文档对的相关度得分
- 作用：在 BM25+向量融合的基础上，通过深度语义重新排序，解决关键词带偏的问题
- 实测效果：Cross-Encoder 重排后 Recall@5 从 0.983 提升至 1.000，MRR@5 从 0.965 提升至 1.000

### Q12：动态 TopK 是如何决策的？
A：`retrievers.py:289-316` 的 `_select_dynamic_topk`：
- 基于得分分布特征自适调整返回文档数量
- 判断逻辑：
  - 如果**首位得分显著高于次位**（top >= 0.85 且 drop >= 0.15）→ 选最少 3 个
  - 如果**平均得分较高**（mean >= 0.85）→ 选最多 8 个
  - 如果**首位得分低**（top <= 0.5）→ 选最少 3 个（防止全错）
  - 否则→ 选基准 5 个
- 受 `dynamic_topk` 配置项控制：min_topk=3, max_topk=8, base_topk=5
- 目的：在精确召all 的同时避免低相关文档污染生成上下文

### Q13：父子索引结构是如何工作的？
A：检索流程中：
- **子块**：小块（如单章节），精准匹配查询关键词，score 单独计算
- **父窗口**：大块（包含多个子块），提供完整上下文，用于 LLM 生成
- `_to_output_doc` (`retrievers.py:318-333`) 时，通过 `_parent_map` 查找父文本：
  ```python
  parent_text = _parent_map.get(candidate.get('parent_id'), child_text)
  return {..., 'content': parent_text, 'child_content': child_text}
  ```
- 这样做的好处：子块命中保证精准，父窗口保证答案可读连贯
- 在 1323 章节块语料上验证：子块命中+父窗口作答，Recall@5=1.0 且答案可读

### Q14：枚举/清单类查询如何处理？
A：`retrievers.py:198-268` 的 `_enumeration_docs`：
- 通过正则检测意图：`有哪些|有什么|列出|列举|清单|全部|所有|多少(个|份|类|种|篇)`
- 如果查询中包含"区别|不同|对比|差异"等关键词，返回空（非枚举类）
- 从数据库查询标题匹配的文档，返回伪文档列表
- 分数采用逆序排列：`score = 1e9 - i`（i 为索引），确保枚举结果优先级最高
- 合并时在 `_hybrid_retrieve` 中：`docs = pseudo + [d for d in docs if d.get('id') not in pseudo_ids]`

### Q15：多租户/密级过滤是如何实现的？
A：`retrievers.py:47-89` 的 `_dense_search`：
- 查询时拼接 SQL WHERE 条件：
  ```python
  filter_dict = {"$or": [
      {"tenant_id": {"$eq": tenant_id}, "doc_level": {"$eq": "public"}, "min_level": {"$lte": clearance_level}},
      {"owner_id": {"$eq": user_id}}
  ]}
  ```
- 如果有 ACL 文档ID：`{"doc_id": {"$in": acl_doc_ids}}`
- Chroma 元数据过滤 + MySQL 授权表双库同步
- 前端按权限显隐：同一个查询，不同租户/密级看到的文档列表不同

### Q16：缓存机制的设计是什么？
A：文档中提到的三级缓存（见 Q7/第70-73行）：
- **L1 精确缓存**：键为问题哈希，值为完整回答。命中率实测 98.7%（547/554 次重复问题命中）
- **L2 语义缓存**：相似问题的模糊匹配，基于嵌入余弦相似度
- **L3 上下文缓存**：对话历史的压缩表示
- 机制：`/api/qa/ask` 入口首检 L1，未命中则检索生成，生成后写回 L1/L2/L3
- 热点问题第 5 次后被自动写回 L1/L2/L3，确保后续直接返回

## 四、被追问时的安全边界
- 缓存命中率：热点问题 L1 精确命中率实测 98.7%（同问题重复压测）；真实多问题场景会低于此值，但三级缓存机制已验证有效，关键论据是"命中即跳过检索+生成，TTFT 近 0"
- 并发上限：Chroma 单机 ~150 QPS 估算值，未做分布式压测验证
- 绝不报编造数字；答"我项目里埋了点，实际跑一下就有，结论是长杆在生成"

### Q17：模型热插拔是如何实现的？
A：`application/rag/model_registry.py` 中的注册表模式：
- LLM/嵌入配置存储在数据库，运行时从 DB 读取活跃模型配置
- `hot_swap_llm()`：切换活跃模型后，即清理语义缓存（L1/L2/L3），确保后续请求使用新模型
- `hot_swap_embedding()`：切换前先探测维度是否兼容，不兼容则要求重建向量库
- **踩过的坑（已修）**：
  ① 启动未加载 DB 激活模型，重启后切换丢失——已修（启动时 `apply_active_models()`）
 ② 嵌入误用 LLM 的 api_key——已修（各自独立的配置项）

### Q18：评测体系是如何搭建的？
A：采用双粒度金标集 + LLM-as-Judge A/B 盲评：
- **57 题双粒度金标集**：文档级 Recall（是否检出正确章节）+ 章节级关键词命中率
- **LLM-as-Judge A/B 盲评**：将模型输出随机排序，让评估人员不知来源，避免偏见
- 实测数据：9B 本地模型 99.3 分（200分制） vs 27B 局域网 95.3 分
- 以评测作为安全网：**零行为变更重构前必须通过评测不下降**，防止“看似更快实际更差”

### Q19：可观测性是如何实现的？
A：Prometheus 埋点 + /metrics 暴露 + Grafana 面板：
- **HTTP 延迟直方图**：全链路 P50/P95/P99
- **检索各阶段 Histogram**：BM25/RRF/Vector/Rerank 各阶段耗时，见性能表格
- **缓存命中/失效计数**：`cache_hit_total`, `cache_miss_total`（L1/L2/L3 计数分离）
- **生成延迟**：SSE 流式生成的 TTFT 和总耗时
- **Locust 压测**：/api/qa/ask P50=53s P95=154s P99=169s，0 失败
- 所有指标通过 `/metrics` 端点实时暴露，Grafana 面板实时展示分解图

### Q20：最大技术挑战和解决方案？
A：OCR 断行导致"检索/评测/验证同时失明"（CJK 不可见换行符），
- 通过正则连通断行：`document_parser.py::_normalize_cjk_text` 用 `_CJK_GAP` 正则
  （`(?<=[\u4e00-\u9fff...])\s+(?=[\u4e00-\u9fff...])`）合并汉字之间的空白/换行
  （"一个月以\n上"→"一个月以上"），数字/拉丁字符旁空格保留（避免"不满 16 周岁"黏连）
- 单测固化预期行为，确保改动不引入回归
- 失明机制：`"在岗天数" in "在岗\n天数"` = False → 检索BM25分词对不上 / 评测kw匹配失败 / 验证金标集失败
- 修复后 Recall@5 从 0.67 恢复 1.0（57 题金标集全数抓回）
- 注意：Recall 是检索指标——"每条金标问题的相关文档是否进入 top-5"，单题二值（1.0/0.0），
  0.67 是 57 题平均值，@5 表示只看前 5 条结果

### Q21：检索回来的 chunk，输入给 LLM 前做了什么处理？
A：⚠️ 诚实答法——**清洗在入库阶段做，拼接层很薄**：
- **清洗（入库时）**：OCR 断行修复（`_normalize_cjk_text`，Recall 0.67→1.0）+ 表格转 markdown
  （`|` 与换行转义为 `<br>`）
- **拼接（生成时）**：`generator.py` 仅 `"\n\n".join(f"文档{i+1}:\n{content}")` 按序号拼装，**无压缩/截断**；
  控制上下文量靠上游 Reranker top_n=8 + 动态 TopK，不在拼接层
- **父窗口**：`retrievers.py::_to_output_doc` 命中子块替换为完整父文本（`_parent_map`），保证上下文完整
- **短板（主动说成 roadmap）**：验证过"检索对不对"（Recall/MRR），**没验证过"喂给 LLM 的上下文质量"**——
  未做有/无父窗口、TopK=3/5/8 对 Faithfulness 的消融；这正说明拼接层还需补评测，是下一步优化方向
